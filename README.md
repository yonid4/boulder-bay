# Boulder Bay

An app that shows Bay Area bouldering gyms, how busy each one currently is, the best time to climb at each, and which gym is the best pick right now based on your location and how crowded each option is.

Monorepo with three parts:
- `backend/` — FastAPI (Python 3.11), managed with `uv`
- `app/` — native SwiftUI iOS app, project generated by XcodeGen from `app/project.yml`
- `supabase/` — migrations for the hosted Supabase project (Postgres + PostGIS + Auth), managed via the Supabase CLI

See `boulder_bay_plan.md` for the full project plan, and `CLAUDE.md` / `backend/CLAUDE.md` for AI-assistant context.

## Prerequisites

| Tool | Why | Install |
|---|---|---|
| Python >= 3.11 | backend runtime | `pyenv install 3.11` |
| [uv](https://docs.astral.sh/uv/) | Python dependency management | `curl -LsSf https://astral.sh/uv/install.sh \| sh` |
| Xcode 16+ with an iOS 17+ Simulator | iOS app | App Store |
| [XcodeGen](https://github.com/yonaskolb/XcodeGen) | generates `BoulderBay.xcodeproj` | `brew install xcodegen` |
| [Supabase CLI](https://supabase.com/docs/guides/cli) | migrations against the hosted project | `brew install supabase/tap/supabase` |
| A Supabase project | Postgres + PostGIS + Auth | [supabase.com/dashboard](https://supabase.com/dashboard) |

macOS is required (Xcode / iOS Simulator). Docker is **not** needed — the database is
the hosted Supabase project, not a local stack.

## First-time setup

```bash
# 1. Backend dependencies + the Chromium build Playwright drives
cd backend
uv sync --all-groups
uv run playwright install chromium
cp .env.example .env       # then fill it in — see "Connecting to Supabase" below

# 2. Point the CLI at the hosted project so migrations can be pushed
cd ..
supabase link --project-ref <project-ref>   # prompts for the database password
supabase db push                            # applies supabase/migrations/

# 3. iOS project
cd app
xcodegen generate          # creates BoulderBay.xcodeproj

# 4. Git hooks (optional but recommended)
cd ..
uv run --project backend pre-commit install
```

### Connecting to Supabase

`DATABASE_URL` and `SUPABASE_URL` are **required** — there is no local Postgres to fall
back on, so the backend fails fast with a clear error rather than quietly pointing at
nothing. Both come from the dashboard:

| Value | Where | Notes |
|---|---|---|
| `DATABASE_URL` | Project Settings → Database | Take the **session-mode pooler (port 5432)**, then swap `postgresql://` for `postgresql+asyncpg://` |
| `SUPABASE_URL` | Project Settings → API | `https://<project-ref>.supabase.co` |

Two traps `app/config.py` now rejects at startup rather than letting you debug at runtime:

- **Port 6543** is Supavisor's *transaction* mode. It breaks asyncpg's prepared statements
  and would force `statement_cache_size=0` + `NullPool`. Use 5432.
- **A missing `+asyncpg`** leaves SQLAlchemy reaching for psycopg2, which isn't installed.

The non-pooled direct connection is IPv6-only and won't resolve on most networks — don't
use it even though the dashboard offers it.

Auth tokens are **ES256**, verified against `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`.
Older tutorials describe an HS256 shared secret; that path no longer applies.

## Daily commands

### Backend
```bash
cd backend
uv run uvicorn app.main:app --reload    # http://localhost:8000
uv run pytest                           # tests + coverage
uv run ruff check . && uv run ruff format .
uv run mypy app                         # strict mode
uv run alembic upgrade head             # apply migrations
uv run alembic revision --autogenerate -m "..."
```

Verify it's up:
```bash
curl http://localhost:8000/health
# {"status":"ok"}
```

### Database

Schema changes go through **Alembic** (`backend/alembic/`), which owns the application
tables. The **Supabase CLI** owns extension/role setup that predates the ORM:

```bash
supabase link --project-ref <ref>   # one-time, per machine
supabase db push                    # apply supabase/migrations/ to the project
supabase migration new <name>       # new CLI-level migration
```

Because everything runs against the hosted project, there is no `supabase start` and no
local reset to hide behind — **a migration you push is applied to the real database.**
Read the diff before pushing, and take a backup from the dashboard before anything
destructive.

### iOS app
```bash
cd app
xcodegen generate                       # after editing project.yml
open BoulderBay.xcodeproj               # then ⌘R
xcodebuild test -project BoulderBay.xcodeproj -scheme BoulderBay \
  -destination 'platform=iOS Simulator,name=iPhone 17'
```

> `BoulderBay.xcodeproj` is **generated and gitignored**. `app/project.yml` is the
> source of truth — add files, targets, and SPM packages there, then re-run
> `xcodegen generate`. Editing the project in Xcode's UI will be overwritten.

The Simulator reaches the backend at `http://localhost:8000` (set via the
`BB_API_BASE_URL` build setting, surfaced to the app as `BBAPIBaseURL` in
`Info.plist`). For a physical device, change that setting to your Mac's LAN IP —
the ATS exception in `project.yml` already permits local-network HTTP. See
`boulder_bay_plan.md` for tunneling fallbacks.

## CI

`.github/workflows/ci.yml` runs on every push to `main` and every PR:
- **backend** — `ruff check`, `ruff format --check`, `mypy app`, `pytest`
- **ios** — `xcodegen generate` then `xcodebuild test`
